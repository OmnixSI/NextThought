1. 目标与范围
目标是让 Windows 版在功能、界面和数据上与 Mac v3.3.0（5ddb9e5 ）对等，并能与 Mac 版
互相恢复备份、共用手机伴侣。
完成的判定标准
1. 功能：第 15 节验收表的每一行都有实机记录，或明确标为「本版不做」并写明原因。
2. 逻辑：Mac 的 592 项 Core 测试在 C# 侧都有对应测试并全部通过。
3. 数据：Mac 导出的 .ntbackup 能在 Windows 恢复，Windows 导出的能在 Mac 恢复，字
段不丢失。
4. 界面：同一批页面的 Mac 截图与 Windows 截图左右对照，颜色、间距、圆角、字号与第 8
节的令牌一致。
5. 性能：冷启动到主窗口可操作不超过 1.0 秒；空闲内存（未加载识别模型）不超过 150
MiB；最终句延迟 p95 不超过 0.8 秒。基线已测到 0.445 秒。
第 5 条的启动和内存数值是目标值，尚无实测；第一次 AOT 发布后按实测修订。

Native AOT 的四条硬规则
AOT 下运行时不能生成代码，反射只能访问编译期可见的成员。下面四条从第一行代码开始执
行，不要等到发布时再改。
1. JSON 一律用源生成。每个工程一个 JsonSerializerContext ，所有可序列化类型用
[JsonSerializable] 登记。工程文件设
JsonSerializerIsReflectionEnabledByDefault=false ，让漏登记的类型在运行时立
即报错。
2. COM 一律用源生成。接口用 [GeneratedComInterface] ，回调对象用
[GeneratedComClass] ，不写 [ComImport] 。基线的 ProcessLoopbackCapture.cs 按
此重写。
3. P/Invoke 用 [LibraryImport] ，结构体全部可直接内存复制，字符串用 UTF-8 指针。不
用 Marshal.SizeOf(Type) 、GetFields() 这类反射写法。
4. 所有工程开启分析器：IsAotCompatible=true 、TreatWarningsAsErrors=true 。
IL2xxx 和 IL3xxx 警告等同编译错误，这样 AOT 问题在普通 Debug 构建时就暴露。
sherpa-onnx 的绑定方式
基线用官方托管程序集的结构体，再用反射把字符串改成 UTF-8（官方绑定按系统 ANSI 编码传
路径，中文路径会失败）。AOT 下改为自写薄绑定：
在 Platform 里声明与 sherpa-onnx 1.13.8 的 c-api.h 逐字段一致的结构体，字符串字段
为 byte* 。
函数用 [LibraryImport("sherpa-onnx-c-api")] 声明，只声明用到的：在线与离线识
别器、流、说话人嵌入。清单以 ZipformerStreaming.swift 调用到的函数为准。
结构体布局错误不会编译报错，只会识别失败或崩溃。所以必须保留基线的 4 段 WAV 回归
（NextThought.Cli 的 asr 诊断），并在 AOT 发布产物上重跑。
升级 sherpa-onnx 版本时，Mac 和 Windows 同时升，并逐字段复核结构体。
AOT 不过时的回退
回退不改变任何源码结构，只改发布参数：PublishAot=false 、
PublishReadyToRun=true 、SelfContained=true 、TieredPGO=true 。代价是安装包变
大、冷启动变慢，功能不受影响。四条硬规则在回退后继续执行，以便以后重新打开 AOT。

依赖规则
1. Core 不引用任何其他工程，不出现 using Avalonia 、using NAudio 、using
Windows.* 。
2. App 只引用 Core 。需要系统能力时调用自己定义的端口接口。
3. Platform 引用 App 和 Core ，只实现端口，不含业务判断。
4. Desktop 引用 App 和 Core 。只有组合根 Program.cs 引用 Platform （Windows 目
标）或 Platform.Stub （其他目标），视图文件不引用。
5. 依赖方向用一项架构测试固定：扫描各程序集的引用列表，违反上述规则即测试失败。
命名与同步规则
Swift 源码是唯一的行为标准，C# 侧不重新设计。

五个最容易出错的地方
1. 值语义。Swift 的结构体和数组赋值即复制，C# 的 List 和类是引用。Swift 里 var copy
= original; copy.items.append(x) 不影响 original ，照抄到 C# 会改到原对象。规
则：数据类型全部不可变，集合属性用 ImmutableArray<T> 或每次新建。
2. 字符串长度。Swift 的 count 按字素簇计，C# 的 Length 按 UTF-16 码元计，表情符号和
部分汉字会差出来。Core 大量按字数截断和计分。规则：在 Core 里提供
Text.Count(s) 、Text.Prefix(s, n) 、Text.Suffix(s, n) ，内部用 StringInfo
按字素簇处理；禁止在移植代码里直接用 Length 和 Substring 表达字数。
3. 字符串比较与大小写。Swift 的 == 、hasPrefix 、contains 按 Unicode 规范等价比
较，不看区域。C# 一律显式写 StringComparison.Ordinal ；lowercased() 对应
ToLowerInvariant() 。localizedCaseInsensitiveContains 对应
CompareInfo.IndexOf(..., IgnoreCase) 。
4. 遍历顺序。Swift 的 Dictionary 和 Set 遍历顺序不固定，源码里凡是需要顺序的地方都
显式排了序。移植时保留每一个 sorted ，排序键用 StringComparer.Ordinal 。Swift
的 sort 不稳定而 OrderBy 稳定，这一点不会造成错误。
5. 整数与浮点。Swift 的 Int 是 64 位，溢出会崩溃；C# 的 int 是 32 位，默认静默溢出。
规则：计数与下标用 int ，字节数、样本数、时间戳用 long ，Core 工程开启
CheckForOverflowUnderflow 。Float 对应 float ，声学特征和向量运算不要升成
double ，否则与 Mac 的结果对不上。

===== PAGE 46 =====
蓝牙的两个问题
第一，Mac 版现在的广播名与手机端对不上。 改名提交 af60a4d 把 Mac 的广播名前缀从
IH- 改成了 NT- （CompanionBluetooth.swift:71 ），但 iOS
（BluetoothCentral.swift:53 ）和 Android（BluetoothTransport.kt:31 ）仍然只接受
IH- 加配对码前 8 位。按代码看，改名之后蓝牙备用通道连不上。这是读代码得出的结论，没
有实机验证。
第二，Windows 不能自定义广播名。 GattServiceProvider 广播时只带服务标识，名字是电
脑的设备名，应用改不了。手机端按名字过滤就找不到 Windows。
两个问题用同一个改动解决，需要改手机端（不属于 Sources/ ，但属于主仓库，要单独提交
并征得同意）：
手机端取消按名字过滤，只按服务标识扫描（两端现在已经带了这个过滤）。
连接后用现有的加密 resync 握手确认身份：解不开第一帧就断开，继续扫描下一个设
备。身份本来就是靠配对密钥保证的，名字只是省一次连接。
在这个改动合入之前，Windows 的蓝牙通道标为不可用，局域网和中转不受影响。
另外，部分蓝牙适配器不支持外设角色。开启前检查
BluetoothAdapter.IsPeripheralRoleSupported ，不支持时开关置灰并说明。
13. 本地化与设置
界面文案和设置项都以 Mac 为唯一来源：文案从字符串目录自动生成，设置项沿用同样的键名
和默认值。
文案
Resources/Localization/Localizable.xcstrings 有 2607 条，源语言是简体中文，每条
都有英文翻译，没有复数变体。键就是中文原文。
生成：写一个脚本 Windows/tools/strings/generate.py ，读字符串目录，生成
Strings.g.cs （一个中文到英文的只读字典）。构建前运行，生成物提交进仓库。不手工
维护第二份翻译。
调用：代码里 L.T("中文原文", 参数…) ，AXAML 里 {l:T '中文原文'} 。界面语言为中文
时直接用键，英文时查字典，查不到时回退到键并记一条日志。
占位符：目录里用到 %@ （160 处）、%lld （127 处）、%.1f 、%.2f 、%% 。L.T 内置一
个小的格式化器直接解析这些占位符，也要支持带序号的写法（如 %1$@ ），因为英文译文
可能调整参数顺序。
Swift 的插值写法：String(localized: "共 \(count) 项") 在目录里的键是 共 %lld
项。移植时按目录里的键写，不按 Swift 源码里的字面写。

不修改 Sources/ 、scripts/ 和 Mac 的签名材料；不提交任何密钥或证书。
安装包
沿用基线的 Inno Setup 每用户安装（Windows/installer/NextThought.iss ）：不需要管理
员权限，每个版本一个独立目录，清单哈希校验，显式回退，卸载保留数据目录。20 项安装生
命周期测试（test_installer_lifecycle.ps1 ）继续作为发布门槛。字体从应用目录加载，
不安装到系统。
自动更新
按 Updater.swift （544 行）和 Core 的 UpdateCatalog 移植，流程与 Mac 相同：
1. 访问 GitHub 的 Releases 接口，按更新通道选出最新的可用版本。
2. 后台下载压缩包，校验 SHA-256。
3. 解压到新的版本目录，用基线的 DeploymentStore 校验清单。
4. 标题栏出现「重启以更新」，用户点击后切换版本并重启。会议进行中不切换。
Windows 侧的约定：
文件名：压缩包 NextThought-<版本>-windows-x64.zip ，安装器 NextThought-<版本>-
windows-x64-setup.exe 。UpdateCatalog 里 Mac 按 -macOS-arm64.zip 后缀选资产
（UpdateCatalog.swift:49 ），C# 侧改为按 -windows-x64.zip 选。
发布位置：Mac 的 README 用「最新版本」链接下载。如果单独发一个只含 Windows 资
产的正式版本，这个链接会指向它，Mac 用户下载不到安装包。所以在功能对等之前，
Windows 版只发预发布版本（标签前缀 windows-v ）；对等之后，Windows 资产挂在与
Mac 相同的版本下。
签名校验：Mac 要求新版本与当前版本是同一签名身份。Windows 在有证书后按同样的原
则校验：新版本的 Authenticode 签名者必须与正在运行的版本一致。没有证书时只校验哈
希，并在「关于」里标明未签名。
