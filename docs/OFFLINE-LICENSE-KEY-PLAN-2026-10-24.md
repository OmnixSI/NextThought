# InterviewHacker 邮件交付限时 Key 方案

整理日期：2026 年 10 月 24 日（Australia/Sydney）。状态：方案文档，尚未实现或部署。

本方案根据后续讨论收敛：用户邮件申请；我们人工审核、人工回信发 Key；用户在 App 内粘贴 Key，在指定时间内使用；激活和日常授权验证均可离线完成，用户不需要连接 Cloudflare。保留现有本地处理与用户模型连接方式，接受专业逆向仍可能绕过本地检查的剩余风险。

**用户实际操作。** 打开 App，粘贴收到的 Key，点击激活。正常客户端验证成功后显示“已激活”和具体到期时间；到期后停止受限功能。设置中可以查看期限、替换 Key 和复制客服诊断信息。到期不删除用户资料，仍允许查看和导出已有记录。

Key 的用途与 API Key 的使用体验相似：用户只需复制粘贴一段文字。常见 API Key 通常由服务器查询和验证；本方案使用包含授权内容及数字签名的离线 Key，App 可以直接验真。为了容纳这些信息，Key 可能比常见 API Key 更长，最终长度由协议确定。

**两种发放方式需要明确区分。** 用户只输入 Key 的界面可以相同，区别在申请邮件中是否需要设备申请码。

| 项目 | 方案 A：持 Key 授权 | 方案 B：发码前绑定设备 |
| --- | --- | --- |
| 申请邮件 | 提交申请理由即可 | 同时粘贴 App 生成的设备申请码 |
| 人工审核后 | 签发有固定期限的 Key | 签发绑定申请设备公钥、有固定期限的 Key |
| App 内激活 | 只输入 Key | 只输入 Key，自动核对本机密钥 |
| 用户访问 Cloudflare | 不需要 | 不需要 |
| 转发 Key | 其他人也能在有效期内使用 | 其他电脑没有对应私钥，正常客户端会拒绝 |
| 重装或换机 | 原 Key 期限不改变 | 换机或设备密钥丢失，需要人工补发 |
| 适用目标 | 流程最省事，接受有效期内共享 | 增加一次复制申请信息，降低普通转发共享 |

建议：如果希望同时兼顾“只输一个 Key”和防止普通转发，采用方案 B。设备信息在申请邮件阶段提供，App 激活阶段不增加额外输入。如果希望申请邮件也完全不含设备信息，可以采用方案 A，但必须接受同一 Key 在有效期内被共享的可能。是否允许有效期内跨设备共享，应在实施前固定为明确的产品规则。

一个重要边界是：**全离线的“首次使用时再绑定”不能实现全球唯一的一机一 Key。** 如果同一 Key 被复制到两台互不联网的电脑，两台电脑都可以把自己当成第一次使用者，各自在本机完成绑定。要可靠限制设备，应在签发前预绑定；若坚持使用时才决定绑定哪台设备，就需要一次对所有设备共享权威状态的在线激活。后一种方式不属于本次完全离线的默认流程。

**人工发放流程。**

1. 用户从网站获取申请邮箱，人工发送申请邮件。方案 B 的用户先在 App 中点击“复制申请信息”，把设备申请码一并放入邮件。
2. 我们人工审核申请，在受保护的后台建立申请记录，选择 3 天或 7 天及适用功能。
3. 我们设定明确的授权开始时间和到期时间。方案 B 同时核对并绑定申请中的设备公钥摘要。
4. 后台使用服务端私钥签名，生成完整 Key。我们手动复制到回信，或附上包含同一内容的授权文件。
5. 用户在 App 中粘贴 Key。App 本地验证签名、产品、期限以及方案 B 的设备关联，成功后保存授权。
6. 正常客户端在启动、睡眠恢复及执行受限功能前检查授权，运行中也检查到期，持续开着软件不能延长期限。
7. 用户需要延期或换机时再次邮件申请。我们人工签发替代 Key，并记录与原授权的关系。

Cloudflare 在这个流程中服务于我们自己的管理与签发工作。用户收到 Key 后，App 无需向 Cloudflare 激活、查询或续验。邮件交付消除了授权链路对用户访问 Cloudflare 的依赖；App 原有的模型服务、搜索或其他联网功能仍然需要各自的网络连接。

**有效期的具体规则。**

| 规则 | 约定 |
| --- | --- |
| 3 天或 7 天 | 分别为连续 72 或 168 小时；签名内容保存明确的开始与截止时刻。 |
| 起算点 | 默认从签发时间开始；管理员也可根据邮件约定预设开始时间。界面明确显示，避免邮件延迟造成误解。 |
| 首次导入 | 导入动作不改变签名中的开始和截止时间。 |
| 重装、重复导入 | 不产生新一轮试用；仍使用原来的固定期限。 |
| 设备补发 | 默认沿用原期限；确有延期需求时，由管理员单独执行并留记录。 |
| 到期行为 | 正常客户端按本机验证结果停止受限功能，保留历史资料和导出能力。 |
| 延期 | 签发包含新截止时间的 Key，用户离线导入即可；不能仅修改后台数据库。 |
| 撤销 | 后台可标记并拒绝未来续发，但无法即时收回已经交付、仍在有效期内的完全离线 Key。 |

为了保持规则可检查，第一版不采用“用户本机第一次激活后再自行计算三天”。完全离线时，服务端不知道真实首次激活时间；如果主要起算依据来自可删除或回滚的本机状态，就可能被重置。固定的签名期限能够直接阻止正常客户端通过重复导入获得新期限，但不能绝对阻止修改系统时间或程序本身。

**Key 的验真方式。** 后台用独立的 Ed25519 授权私钥签名，App 只内置验签公钥。Key 的授权内容至少关联产品、协议版本、许可证 ID、签发时间、开始时间、到期时间、适用功能以及签名 key ID；方案 B 再包含设备公钥摘要。修改截止日期、功能或设备信息会使原签名失效。实现采用平台密码学 API 和固定协议，不自行设计签名算法。[Cloudflare Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/) · [现成客户端验签约定](https://github.com/bmpenuelas/workers-license-server/blob/ee12b26aeb06200d70bf89629fb9703a4b8b9ebf/docs/CLIENT-INTEGRATION.md)

验证必须检查真正的签名、固定算法和受信任公钥，再使用授权内容。Base64 解码和普通字符串校验不能证明 Key 是我们签发的。公钥不得由待验证 Key 自己临时指定并直接信任。Key 不应包含原始邮箱、模型 API Key、录音、截图或其他用户内容。

离线 Key 可以在同一设备重复导入。这里不能承诺服务器意义上的“一次性兑换”，因为导入结果没有回传给服务器。方案 B 通过预绑定设备和固定期限降低复用风险，后台只记录签发和补发，不能据此显示“用户已经激活”或“最近使用时间”。

**方案 B 的设备申请码。** App 在本机生成设备签名密钥，申请码仅包含公钥、摘要和必要版本信息，不读取 MAC 地址、主板序列号或个人资料。后台核对公钥并把其摘要签入 Key。

macOS 上优先采用 Secure Enclave P-256 密钥，并把恢复材料保存在本机 Keychain。Apple 说明相应恢复材料只能由原设备的 Secure Enclave 使用，有助于防止直接把密钥复制到另一台电脑。实际实现要检查硬件可用性，兼容模式应明确标注较弱的保护范围。[Apple Secure Enclave 密钥保护](https://developer.apple.com/documentation/security/protecting-keys-with-the-secure-enclave) · [CryptoKit Keychain 存储](https://developer.apple.com/documentation/cryptokit/storing-cryptokit-keys-in-the-keychain)

导入 Key 时以及开始受限会话时，本机应确认能够使用对应私钥，不能只比较一个可编辑的设备字符串。设备私钥及授权状态不得通过普通资料备份导出并自动迁移。设备绑定降低直接转发的可行性；它仍不能证明客户端原封不动，也不能阻止原设备被用于转发签名或运行修改过的程序。

**本地时间防护。** 签名能保护许可证中的截止日期，电脑当前时间仍属于本地输入。第一版应加入以下合理防护，并清楚记录剩余风险。

| 场景 | 处理方式 |
| --- | --- |
| 正常使用时修改系统日期 | 结合进程内连续计时和已记录的最大时间，避免系统时间回退直接增加可用时长。 |
| 电脑睡眠 | 使用包含睡眠时段的连续时钟，恢复时重新检查截止时间。 |
| 重启或重新启动 App | 检查持久化的时间锚点和签名中的时间范围；连续时钟不能作为跨重启的绝对世界时间。 |
| 明显时间回拨 | 显示明确的时钟异常和联系支持入口；不能自动重开试用或无限期放行。 |
| 删除授权状态 | 要求重新导入原 Key；Key 的固定到期时间不改变。方案 B 的设备密钥丢失走人工补发。 |
| 系统快照回滚或高级篡改 | 不能可靠保证识别，列为接受的剩余风险。 |

Apple 的 ContinuousClock 包含系统睡眠期间的计时，但其时间点只适合本地运行期间比较，不能把它当成可持久化的可信日历。[Apple ContinuousClock](https://developer.apple.com/documentation/swift/continuousclock)

这些措施可以增加简单改日期的成本，不能构成完全离线的可信时间系统。成熟授权平台的文档同样明确指出，纯离线场景不能完全解决本机时钟篡改。[Keygen 离线时间安全说明](https://keygen.sh/docs/api/security/#clock-tampering)

**客户端防护范围。** 目标是增加普通篡改和批量分享的成本，接受专业逆向仍可能绕过。是否擅长逆向并不等同于是否需要面试工具；即使只有少数人能修改程序，修改后的版本也可能被分享，因此保护评估仍需覆盖传播风险。

首版应集中做好：固定公钥验签；严格解析授权；统一核心授权状态；覆盖实时回答、手动回答、截图回答、重新生成、复盘和后台等入口；运行中持续检查到期；正式构建使用优化与去除无用调试信息；检查 App 自身必要文件的完整性；依据实测考虑适量混淆和反调试。自检不能误伤正常系统工具和会议使用场景。[OWASP 防逆向与篡改说明](https://mas.owasp.org/MASVS/11-MASVS-RESILIENCE/)

这些措施保护的是正版客户端的正常行为和许可证真实性，无法保证用户永远不能修改本地判断。本次按用户选择保留本地能力，核心功能迁到云端不作为本方案前提。用户自己的模型密钥和登录凭证继续留在原有安全存储中。

应用签名与授权签名分别管理。后续本机构建沿用既有 `InterviewHacker Local Signing` 身份、Bundle ID `com.interviewhacker.app` 和 designated requirement；不因增加授权功能而轮换应用证书或重置隐私权限。完整性校验需兼容项目现有的本机重新签名更新流程。[项目签名约束](/Users/spdor/Desktop/CodeSpace/InterviewHacker/AGENTS.md)

**Cloudflare 管理后台。** 后台可由受 Access 保护的 Worker 与 D1 组成；只允许管理员进入，覆盖生产和预览入口。数据库记录申请、采用的方案、许可证 ID、设备摘要（若有）、固定期限、签发人、签发版本、补发和延期关系；签名私钥放在 Worker Secret，并作受控加密备份。[Worker Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) · [Worker Secrets](https://developers.cloudflare.com/workers/configuration/secrets/)

用户不调用授权 API，日常负载主要来自人工管理和发码，较适合从免费额度内开始验证；域名、现有邮箱、实际资源用量与供应商政策仍分别计算。签发动作需防重复提交，避免一次操作重试生成不同期限的多份有效 Key。管理员界面明确显示起止日期与时区，并在生成前确认授权对象。

后台“撤销”只影响签发记录和未来补发，界面必须写清“已交付的离线授权仍可用至原截止时间”。离线方案不显示虚构的实时在线状态、设备最后登录或即时封禁结果。后台数据库恢复也不会自动撤回已经发出的签名 Key；需要保留签发审计和私钥恢复流程。

**上线前验证。**

| 类别 | 必测情况 |
| --- | --- |
| 完全离线 | 从收到 Key 开始关闭网络，完成导入、使用、重启、睡眠恢复和正常到期；整个授权路径不访问 Cloudflare。 |
| 签名真实性 | 修改日期/功能/产品/设备字段，伪造或截断签名，替换公钥，未知 key ID，重复字段、超大或损坏输入。 |
| 期限 | 明确起止边界、跨时区、夏令时、重复导入、过期 Key、尚未开始的 Key。 |
| 改时钟 | 回拨、前拨、冻结系统日期、重启、睡眠和本机状态缺失；记录误拒绝及未覆盖情况。 |
| 设备 | 方案 A 的跨机器共享属于预期行为；方案 B 将同一 Key 和恢复材料复制到另一台电脑应被正常客户端拒绝。 |
| 发放与补发 | 管理员重复点击、请求响应丢失、原期换机、人工延期、遗失 Key、密钥轮换和签发审计恢复。 |
| 功能入口 | 各种回答、复盘、后台与手机入口统一执行授权，到期后不继续启动新受限任务。 |
| 数据和更新 | 到期不损害用户资料；授权私钥不进入普通备份；应用更新和本机签名保持兼容。 |
| 防护效果 | 验证一般修改与复制的阻力，记录实际发现的绕过；不以未经测试的“不可破解”描述效果。 |

**实施顺序。** 先固定两种方案的字段与验签协议，以及签发时确定期限的规则；再完成 Cloudflare 人工签发后台和 App 的单 Key 输入；随后补齐本地计时、方案 B 的预绑定及程序自身防护；最后执行离线、期限、复制、更新和误拒绝验证，再邀请少量真实用户试用。

本方案不需要用户访问 Cloudflare，因此授权激活不会因其大陆连通性直接失败。保护强度以实际实现和验证为准；有效期内的 Key 共享、离线撤销和高级篡改，必须按所选方案分别理解。
